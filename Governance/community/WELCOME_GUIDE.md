# Newcomer Welcome Guide

## Purpose

Welcome to TeachLink Web. This guide gets a newcomer from "I'm interested" to a
first contribution: what to do first, which resources to read, and where to ask
for help. You do not need to be an expert, and you do not need permission to
start.

## Scope

This guide is for anyone new to the project, whether you plan to write code,
improve documentation, report bugs, help with design or translation, or answer
questions. It is a starting map; the linked documents are the authoritative
source for each topic.

## First Steps

A good first week looks like this:

- **Read the basics.** Skim the repository [README](../../README.md) to see what
  the project is and how to run it, then read the [Mission](../MISSION.md) and
  [Values](../VALUES.md).
- **Read the rules of the road.** Read the [Code of
  Conduct](../CODE_OF_CONDUCT.md) and the [Communication
  Norms](../policies/COMMUNICATION_NORMS.md). They apply to everyone, every
  time.
- **Set up locally.** Follow the setup steps in the README and
  [CONTRIBUTING.md](../../CONTRIBUTING.md) so you can build and run the checks
  before you change anything.
- **Find something small.** Browse issues labelled for newcomers, following the
  [good first issue policy](../policies/GOOD_FIRST_ISSUE.md). Comment that you
  would like to take one, and wait for a maintainer to confirm so work is not
  duplicated.
- **Open your first pull request.** Keep it small and focused, link the issue,
  explain what changed, and sign off your commits as described in the [DCO
  policy](../policies/DCO.md).
- **Expect feedback.** Review comments are a normal part of the process and are
  about the change, not about you. See the [Review
  Policy](../policies/REVIEW_POLICY.md).

## Key Resources

Keep these close:

- [CONTRIBUTING.md](../../CONTRIBUTING.md) - branching, checks, and the pull
  request workflow.
- [Governance README](../README.md) - how decisions are made and where each
  policy lives.
- [Scope](../SCOPE.md) - what the project does and does not take on, so you know
  whether an idea fits.
- [Label taxonomy](../LABEL_TAXONOMY.md) - what the issue and pull request
  labels mean.
- [Contributor role](../roles/CONTRIBUTOR.md) and the [onboarding
  process](../processes/ONBOARDING.md) - what to expect as you take on more.
- [Security Policy](../SECURITY_POLICY.md) - how to report a vulnerability
  privately; never post one in a public issue.

## Where to Get Help

You are never expected to struggle alone:

- Ask a question on the issue you are working on, in the pull request, or in
  GitHub Discussions when it is enabled, so the answer helps the next person
  too.
- Join the community office hours when they are running (see the [onboarding
  process](../processes/ONBOARDING.md) and the office hours policy in this
  folder).
- If you are stuck on process, ask a maintainer to point you at the right
  document; if a document is wrong or unclear, fixing it is a great first
  contribution.
- If anyone behaves in a way that makes you uncomfortable, use [Code of Conduct
  reporting](../COC_REPORTING.md).
- If you are stuck for several days with no reply, follow the [escalation
  path](../processes/ESCALATION_PATH.md).

## Ownership and Review

- Maintainers own this document and are accountable for applying it
  consistently.
- Anyone who finds the guide out of date is encouraged to fix it; a maintainer
  checks the links and steps at least once per release cycle.
- Changes are proposed in a pull request that touches only the `Governance/`
  folder and are reviewed like any other governance change (see the [Review
  Policy](../policies/REVIEW_POLICY.md)).
- This document is versioned with the repository and describes how the project
  actually operates rather than an aspiration.

## Success

This guide succeeds when a newcomer can find the next step without asking, makes
a first contribution they are proud of, and feels welcome doing it.
