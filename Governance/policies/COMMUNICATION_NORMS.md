# Community Communication Norms

**Version:** 1.0

## Purpose and Scope

These norms set expectations for communication among TeachLink Web contributors,
maintainers, and community members. They apply to project-related communication
in the official channels below. They complement the project's conduct and
security policies; they do not replace them.

## Official Channels

- **GitHub Issues** are for actionable bug reports, feature requests, and
  project questions that need tracking.
- **GitHub Discussions**, when enabled for this repository, are for open-ended
  questions, ideas, and community conversation. If Discussions are unavailable,
  use an appropriate issue.
- **Pull requests** are for proposing code or documentation changes and keeping
  review feedback and decisions with the proposed change.
- **Security reports** must use the repository's private vulnerability
  reporting channel when available. Otherwise, contact a maintainer privately.
  Do not publish suspected vulnerabilities, exploit details, credentials, or
  personal data in an issue, discussion, or pull request.

Project decisions and actionable outcomes should be recorded in the relevant
repository issue, discussion, or pull request so they remain accessible and
searchable. Do not share private contact details or sensitive information in
public channels.

## Tone and Etiquette

- Be respectful, inclusive, and professional. Critique proposals and work, not
  the people behind them.
- Be clear and constructive: provide relevant context, describe the impact, and
  suggest a next step when practical.
- Assume good faith, while listening carefully when someone explains that a
  message or action caused harm. Correct misunderstandings without personal
  attacks or escalation.
- Keep discussion focused and accessible. Avoid repeated messages, personal
  call-outs, and cross-posting the same request to pressure a faster response.
- Harassment, discrimination, threats, insults, and deliberate disruption are
  not acceptable. Moderation and conduct concerns should be raised privately
  with a maintainer rather than argued out in a public thread.

## Response Expectations

TeachLink Web is maintained across time zones and availability varies. The
following are targets, not guarantees or on-call commitments:

- A maintainer should aim to acknowledge a new issue or discussion within three
  business days.
- A pull request should aim to receive an initial review or status update within
  five business days.
- If a response is delayed, contributors should add one concise follow-up to the
  original thread after five business days. Avoid repeated pings; maintainers
  will update the thread when they can.
- Security reports should be acknowledged promptly through the private channel,
  but are handled under the security response process rather than these public
  response targets.

Business-day targets do not require anyone to respond outside their normal
availability. If a request is time-sensitive, explain the reason and impact in
the original thread without implying guaranteed priority.

## Ownership and Changes

Maintainers own this policy. Changes are proposed through a pull request that
touches only the `Governance/` folder, in accordance with the governance
contribution rules.
