# TeachLink Governance: Formal Voting Process

**Version:** 1.0.0  
**Status:** Active  
**Scope:** All formal governance proposals, major architectural changes, and core policy modifications across the TeachLink ecosystem.

---

## 1. Purpose
To ensure transparent, accountable, and structured decision-making across all TeachLink repositories, this document defines the exact triggers requiring a formal vote, voter eligibility criteria, and mandatory result recording procedures.

---

## 2. Triggers Requiring a Formal Vote
A formal vote must be initiated for any of the following actions:
* **Core Governance Changes:** Amendments to project policies, voting quorums, tie-breaking rules, or governance processes.
* **Major Architectural Proposals (RFCS):** Introduction of breaking changes, migration of core databases/frameworks, or adoption of new protocol standards.
* **Maintainer Membership:** Addition or removal of core maintainers and working group leads.
* **Deadlocked Discussions:** Any pull request or issue where informal consensus cannot be reached after 7 days of open discussion.

---

## 3. Voter Eligibility
* **Active Core Maintainers:** Individuals holding documented commit access and active participation status on core repositories are eligible to vote.
* **Conflict of Interest Disclosure:** Any eligible voter with a direct commercial or personal conflict of interest regarding a specific proposal must recuse themselves or explicitly register their abstention.

---

## 4. Recording Results
1. **Public Archival:** All formal votes must be conducted via GitHub Discussions, governance pull request comments, or immutable voting threads.
2. **Tabulation:** The voting outcome, individual ballots (where applicable), and final tally must be documented clearly in the issue description or governance commit log.
3. **Execution:** Upon successful tally verification and achievement of quorum, implementing issues are created and tagged with the approved governance label.
